Phase 3 — Component Relationship Graph

Why Graph vs Vector for Relationships

"What replaces the TPS62902?" is a structural fact, not a semantic similarity question. The answer is stored as an explicit edge in a graph. A vector search might accidentally find the TPS62903 datasheet if its text mentions TPS62902, but that is coincidence — not a reliable structural answer.

Graph traversal is O(hops) — very fast. Vector search for "what replaces X" would require the model to extract the replacement from prose, which is unreliable and slow.

Data Model

Nodes:   (:Component {name, type, vendor})
Edges:   -[:REPLACED_BY]->
         -[:PIN_COMPATIBLE]->
         -[:FUNCTIONALLY_SIMILAR]->

Example:
  (TPS62902) -[:REPLACED_BY]-> (TPS62903)
  (LM358)    -[:PIN_COMPATIBLE]-> (TLV2372)
  (LM358)    -[:REPLACED_BY]-> (TLV2372)

Cypher vs Gremlin — Same Query

graph.py — Cypher (local Neo4j)

MATCH (a:Component {name: 'TPS62902'})
      -[:REPLACED_BY]->(b)
RETURN b.name

graph_alternative1.py — Gremlin

g.V()
 .has('component','name','TPS62902')
 .out('REPLACED_BY')
 .values('name')

Both return the same result. Cypher is more readable. Gremlin is required for Neptune (AWS). The graph.py and aws/graph_neptune.py expose the same Python interface (find_replacements(), find_pin_compatible()) — callers don't know which language ran underneath.

Gremlin MERGE Pattern (important for Neptune)

# Gremlin doesn't have MERGE like Cypher.
# The coalesce pattern achieves the same thing (create if not exists):
g.V().has('component','name', name)
 .fold()
 .coalesce(
     unfold(),                          # return existing if found
     addV('component').property('name', name)  # create if not found
 )

Multi-hop Traversal

# Cypher — find components within 2 hops:
MATCH path = (a {name: 'TPS62902'})-[*1..2]->(b)
RETURN b.name, type(last(relationships(path))) AS rel, length(path) AS hops

# Gremlin equivalent:
g.V().has('name','TPS62902').repeat(out()).times(2).values('name').dedup()
