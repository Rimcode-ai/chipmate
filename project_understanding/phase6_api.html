Phase 6 — FastAPI + Redis

Rate Limiting: Sliding Window

Why sliding window over fixed window?

Fixed window: 10 requests/60s, resets at :00
  A client sends 10 at :59 and 10 at :01 → 20 requests in 2 seconds.

Sliding window: the 60-second window moves with each request
  Always at most 10 requests in any 60-second window.

Redis sorted set algorithm:
  1. ZREMRANGEBYSCORE key 0 (now - 60s)  ← remove old entries
  2. ZADD key now now                     ← add current request
  3. ZCARD key                            ← count in window
  4. EXPIRE key 60                        ← auto-cleanup
  5. If count > 10: return 429

Semantic Caching

Cache key: MD5(query.lower()) → 32-char hex string
TTL: 5 minutes (300 seconds)
Store: Redis SETEX key 300 json_value

Why MD5 over embedding similarity:
  Embedding similarity requires an embedding call to look up the cache (50-200ms overhead).
  MD5 is instantaneous and works for exact/near-exact repeated queries.
  For a demo system, exact-match caching is sufficient and more explainable.

Redis vs In-Memory

main.py — Redis (USED)

  • Survives process restart
  • Shared across multiple workers
  • Redis sorted sets for sliding window
  • Requires Docker (redis container)

main_alternative1.py — In-memory

  • No Redis dependency
  • Counter resets on restart
  • Not shared across workers (bypasses limit at scale)
  • Good for understanding the algorithm

Run + Test Commands

uvicorn local.main:app --reload --port 8000
# Happy path:
curl -X POST http://localhost:8000/query \ -H "Content-Type: application/json" \ -d '{"query": "What is the voltage of TPS62902?"}'
# Rate limit (fire 11 requests, 11th returns 429):
for i in $(seq 1 11); do curl -s -o /dev/null -w "%{http_code}\n" \ -X POST http://localhost:8000/query \ -H "Content-Type: application/json" \ -d '{"query": "test"}'; done
# Cache test (run same query twice, second is faster):
time curl -X POST http://localhost:8000/query \ -d '{"query": "What is the voltage of TPS62902?"}' \ -H "Content-Type: application/json"
# Health check:
curl http://localhost:8000/health
Interview talking point: "I implemented a sliding window rate limiter in Redis using sorted sets. The fixed window has a burst problem at the boundary — sliding window doesn't. For caching I used MD5 keying instead of embedding similarity because the lookup is instant and doesn't add latency to a cache hit."
