Phase 2 — Hybrid Search

Why Hybrid Search

Vector search alone fails on exact-match queries. "TPS62902 input voltage" — the exact phrase "input voltage" might not have high cosine similarity to "what is the operating voltage of TPS62902?" if the datasheet uses different phrasing. Keyword search (BM25/FTS) catches exact token matches.

Neither alone is best. Hybrid combines both and uses Reciprocal Rank Fusion (RRF) to merge the two ranked lists.

Reciprocal Rank Fusion Formula

RRF(d) = Σ  1 / (k + rank_i(d))
          i

Where:
  k = 60  (standard smoothing constant — reduces the weight of top ranks)
  rank_i = rank of document d in ranker i (1 = best)
  Σ sums over all rankers (vector search + keyword search)

A document appearing in rank 1 of both lists scores: 1/(60+1) + 1/(60+1) = 0.0328
A document in rank 1 of one list only scores:        1/(60+1)             = 0.0164

Why RRF over weighted sum (0.7*vector + 0.3*bm25)

Cosine similarity returns values in [0, 1]. BM25 returns unbounded positive floats. You can't add them directly — 0.8 cosine + 12.4 BM25 is meaningless. RRF only uses ranks, so scale differences don't matter.

Three BM25 Options

retrieve.py — tsvector (USED)

  • Built into every Postgres install
  • GIN index for fast lookup
  • plainto_tsquery converts plain text
  • Not true BM25 — uses tf-idf variant
  • Sufficient for our 10-20 doc corpus

retrieve_alternative1.py — rank_bm25

  • True BM25Okapi in Python
  • Loads ALL chunks into memory (O(n))
  • No extra DB extension needed
  • Slow at scale (>100k chunks)

retrieve_alternative2.py — pg_bm25 (ParadeDB)

  • True BM25 inside Postgres
  • Requires paradedb/paradedb Docker image
  • @@@ operator and paradedb.score()
  • Production-grade but non-standard extension

embed_alternative1.py — sentence-transformers

  • In-process model (no Ollama needed)
  • all-mpnet-base-v2: same 768 dims
  • Native batch_size support
  • Loads ~420MB into Python process

Postgres Schema (must run before embed.py)

-- Run inside: docker compose exec postgres psql -U chipmate -d chipmate

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    chunk_id    TEXT PRIMARY KEY,
    component   TEXT NOT NULL,
    section     TEXT,
    page        INTEGER,
    text        TEXT NOT NULL,
    embedding   VECTOR(768),          -- nomic-embed-text dimension
    fts_vector  TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', text)) STORED
);

-- ANN index: approximate nearest neighbor (much faster than exact scan)
-- ivfflat with lists=100 is good for up to ~100k rows
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- GIN: inverted index for fast full-text search
CREATE INDEX ON chunks USING GIN (fts_vector);

Run Commands

# Connect to Postgres and create schema:
docker compose exec postgres psql -U chipmate -d chipmate
# Embed and store chunks:
python -m local.embed --input data/chunks/TPS62902.json
# Test retrieval:
python -m local.retrieve --query "operating voltage TPS62902"
python -m local.retrieve --query "what replaces TPS62902" --top-k 5
Interview talking point: "I used hybrid retrieval: pgvector for semantic similarity and Postgres FTS for keyword matching, fused with Reciprocal Rank Fusion. RRF is more stable than a weighted sum because it only uses rank positions, not raw scores — cosine similarity and BM25 are on incompatible scales."
